# E19 WordPress Connector plugin and sync engine

Milestone: standalone (Deploy). Depends on: the Servers vault (`SecretEnvelope`, sealed key
stores) and the Deploy IPC patterns from E07.

## Goal

Reach WordPress sites that have no SSH, no FTP and no other way in, through a plugin the site owner
installs from wp-admin. Runova pairs with the plugin using a one-time key and then pulls and
deploys theme, plugin and mu-plugin files over signed HTTPS calls. A deploy never leaves a site
broken: every change is staged, syntax checked, snapshotted, applied, health checked, and rolled
back on its own when the site stops answering. Agent settings and Runova's own files never leave
the computer.

## Acceptance criteria

1. A connection key works once, for 15 minutes, and is good for read or write as the WordPress
   admin chose. A read key cannot reach any write route.
2. Every request is signed and checked for freshness and replay; every reply is signed with the
   site key that came in the connection key. A changed byte anywhere fails the call.
3. Calls work over `/wp-json/`, over `?rest_route=` on sites with plain permalinks, and over
   admin-ajax when the REST API is blocked.
4. A deploy with a PHP syntax error is refused before anything is written. A deploy that makes the
   site fail its health check is rolled back without the user doing anything, and so is one that
   fatals the site so badly that the plugin's own routes stop answering.
5. Files under agent and Runova folders (`.claude`, `.agents`, `.runova`, `.cursor` and the
   rest), `AGENTS.md`, `CLAUDE.md`, `.mcp.json`, `.env` files and version control folders are never
   sent. The plugin refuses them on its own too.
6. The site owner can see every connection, revoke it, read the audit log and roll back a deploy
   from wp-admin, and can switch everything off with `DISALLOW_FILE_MODS` or the connector's own
   constants.

## Implementation notes

- Wire format: every call is a `POST multipart/form-data` with `am_auth` and a gzip `bundle`, so it
  survives hosts that strip headers and firewalls that flag `.php` in request bodies. The bundle is
  signed by its hash, which keeps pure-PHP verification cheap.
- Ed25519 everywhere: Node has it natively, and WordPress ships `sodium_compat`, so the plugin
  needs no PHP extension.
- Recovery when deployed code fatals every request: the client asks `/rescue/status` first (the
  guard answers it before themes and plugins load) and rolls back through `/rescue/rollback`, so
  the result is "rolled back, fatal error" rather than an error page.
- The connector can update itself. A write connection lists the files of the plugin zip the app
  ships; the site downloads that release from GitHub when it can (only that address, and only
  when every file matches the signed list), and otherwise the app sends the files as blobs. No
  ZipArchive either way. The plugin builds the new folder beside
  the old one, parses it, swaps with two renames and health checks the site, putting the old
  folder back on a regression. This gives a write key no new power: it can already deploy PHP
  into any active plugin or theme. The first update of a connector that predates the route still
  needs one manual upload; `selfUpdate` is how the app tells the two apart.
- A clone (staging copy, database restore) shares `wp_options`, so the plugin renews its site key
  and revokes every connection when the `home` address changes, and the desktop only merges a
  reconnect with an existing site when both the key and the REST origin match.

## Verification

- Shared vectors (`vectors/protocol-v1.json`) pass on both sides: Vitest in core, PHPUnit on PHP
  7.4 and 8.3 (ext-sodium and sodium_compat).
- Plugin: 200 PHPUnit tests (all 42 state and action pairs, journal resume, the admin views with
  hostile labels), `php -l` on 7.4, 8.0, 8.3 and 8.4, PHPCompatibilityWP and the WordPress security
  sniffs, and a smoke run on real WordPress 7.1.2: 91 checks single site, 20 multisite.
- Desktop: `wordpress.int.test.ts` runs the real sync engine against the real plugin in Docker
  (pairing, a project, a deploy with agent files left in the theme, a refused syntax error, a fatal
  error rolled back by the guard, a manual rollback, a read-only key).
- App: `e2e/deployWordPress.e2e.ts` drives the built app through the same story, which also proves
  Ed25519 under Electron's BoringSSL. It passes on the final code, after the security fixes, and
  runs nightly as `wordpress-e2e`.
- A packaged build (`electron-builder --dir`) carries the zip at
  `resources/wordpress-connector/runova-connector.zip`, byte for byte the built one, which is
  where "Download the plugin" reads it.
- Uninstall, single site and multisite: a pending deploy is rolled back at deactivation, the tables,
  options, data folder and guard go, and every theme, plugin and mu-plugin file is unchanged. Use
  `wp plugin uninstall`; `wp plugin delete` removes files without running `uninstall.php`.
- An independent security review (2026-10-05) found a stored XSS in the wp-admin confirm prompts
  that could turn a read key into code execution, audit log flooding, a shared-IP lockout of the
  paired app, pulls not bound to the reviewed manifest, an upload that re-read files after
  hashing, clone confusion, and credential files missing from the deny list. All are fixed with
  regression tests.
